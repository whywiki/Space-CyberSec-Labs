  flooding the log with noise.
- The security mechanism needed is message authentication — specifically HMAC or a
  digital signature — so the receiver can verify that each message was produced by
  the legitimate satellite and has not been forged or modified in transit.

- HMAC alone is not sufficient because a valid signed message captured from the
  channel can be resent verbatim. The HMAC verifies correctly since neither the data
  nor the signature has changed, so without extra state the receiver cannot tell the
  message is old.
- Timestamp prevents replay because the receiver tracks the last accepted timestamp
  per satellite. Any message whose timestamp is equal to or earlier than the stored
  value is rejected, regardless of its valid HMAC. A legitimate new message always
  carries a strictly later timestamp.
- Limitations: relies on clocks being monotonic and reasonably synchronized; if the
  satellite clock is reset or drifts backward, legitimate messages get rejected.
  The state file is in memory/process scope only — a receiver restart clears the
  last-timestamp database, opening a window where old messages would be accepted
  again. Additionally, an attacker with a very recent valid message could replay it
  within the same second if the sender fires multiple messages per second.

=== FINAL REFLECTION ===

- What was possible in the insecure telemetry channel?
  Any process on the network could read all telemetry in plaintext, inject arbitrary
  messages, and impersonate any satellite — the receiver accepted everything without
  question.

- Which attacks were blocked by HMAC?
  Message forgery (crafting a new fake message), message modification (changing any
  field of an intercepted message), and impersonation of the satellite without
  knowing the shared secret.

- Which attacks were still possible after adding HMAC?
  Replay attacks: a valid signed message captured from the channel could be resent
  and accepted again because HMAC carries no freshness information.

- Why was replay protection needed as a separate mechanism?
  HMAC only proves that the message was produced by someone who knows the secret and
  that its content was not altered. It says nothing about when the message was
  created or whether it has already been delivered. Preventing replay requires
  stateful freshness checks (timestamps or sequence numbers) that go beyond what a
  MAC can provide.

- Why does this laboratory still not provide confidentiality?
  Neither HMAC nor timestamp checks encrypt the payload. All fields — SAT_ID,
  TIMESTAMP, VALUE, and SIGNATURE — are transmitted as plaintext TCP. Any observer
  on the path can still read the telemetry content in full.

- What additional protections would be needed for the command channel?
  Encryption (e.g. TLS or symmetric encryption) to provide confidentiality; mutual
  authentication so the satellite also verifies the ground segment's identity;
  stricter replay protection with sequence numbers rather than timestamps alone; and
  possibly asymmetric signatures so the signing key never leaves the satellite.
